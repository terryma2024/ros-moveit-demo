## 1. 用户裁定

2026-10-13 至 2026-10-14 的讨论中，用户确定了以下各点：

1. 方向是"容器只是隔离外壳"。
2. 提供一个脚本，使主机环境（各依赖库的版本）和 Docker 镜像同步更新；主机升级后一键升级镜像。
3. 镜像里提供编译脚本。主机上的 install 目录由容器实例编译，前提是环境一致。
4. macOS 直接在主机构建；macOS 不支持 Docker 多 worker，只支持主机执行。
5. 多 worker 模式的 shard 容器启动时挂载 install 目录。
6. 只做 shard。推理服务容器不在范围内：推理代码相对稳定，推理代码没有变动就不应更新推理镜像。
7. Python 虚拟环境挂载主机那一份。
8. 环境清单不一致时拒绝启动。
9. 先成文，执行后置。
10. 已知约束：ai-station 和 antzb 都是 Ubuntu，但主机环境不完全一致。

受管包暂停自动升级的做法（第 5.3 节）由协调者提出，用户在得到说明后要求成文，尚未单独逐条确认。

## 2. 范围

目标

- 同一台主机上，原生单 worker 和 shard 容器运行同一份 install 目录和同一个 Python 虚拟环境，包括编译产物。
- 改代码后不重建 shard 镜像；shard 镜像只在主机受管环境变化时重建。
- 环境一致由校验强制，不靠假定。

非目标

- 不改推理服务镜像的构建、内容和启动方式。
- 不改单向控制协议、固定 ROS 标识、任务输出布局、Teacher 策略、QC 和任何判定规则或阈值。
- 不追求镜像跨主机移植；框架镜像与主机一一对应。
- 不在 macOS 上使用容器。
- 不定义真实硬件运行。

## 3. 现状

以下各点已核实，除非另有说明。

- 两个镜像都把项目代码烧在镜像里：构建时把源码快照复制到 `/act/source`，在镜像内 colcon 构建到 `/act/install`
  （合并安装），运行时不挂载代码。shard 镜像是多阶段构建。
- 两个镜像共用一条入口链：`/act/bootstrap.bash` → `image_bootstrap` → 角色程序，逐级 `exec`，最终 pid 1 是业务主进程。
- 入口启动时读 `/act/provenance.json`，重新计算 `/act/source` 和 `/act/install` 的哈希并核对，不符则拒绝启动；主机在容器启动后
  用 `docker exec` 再读回一次。除此以外，运行期没有任务逻辑读取 `/act/source`（检索范围不含第三方子模块）。
- 运行时挂进 shard 的只有数据和配置：实例自有根目录及其 `output`、`control`，冻结输入、运行时配置、权重、采集配置、规格
  文件，以及两个 IPC 目录。
- 同一提交下，shard 镜像与主机门禁安装目录里的 Python、launch、配置共 1053 个文件，1052 个逐字节相同；例外是一个各自编译的
  Python 扩展模块。C++ 产物各自编译，未逐个比对。
- Python 环境是两套：容器用 `/act/venv`；主机用 `/data/work/venvs/so101-grounded-sam` 加一个冻结的依赖目录。
- shard 镜像的基础层是较早构建的 ROS Jazzy 推理镜像，其中 `ros-jazzy-*` 的版本固定在当时。主机的同名包是 2026-10-06 的版本。
  两边具体差多少未核实。
- 合同校验要求推理镜像和 shard 镜像的源码包哈希相等（`parallel_collection_contracts.py` 的 `validate_controlled_identity`）。
  用户已表示这条可以去掉。
- ai-station 的包管理现状（2026-10-14 只读读取）：自动升级开启并每天运行；没有任何包被锁定；自动升级只允许 Ubuntu 官方源及其
  安全更新源，ROS 包来自另一个源，不会被自动升级。2026-10-13 下午的两次环境变化都不是自动升级造成的：一次是手动安装
  RealSense 相关包，一次是图形界面软件更新提交的升级，其中包含 NVIDIA 驱动，随后主机重启。antzb 的配置未核实。

## 4. 架构

### 4.1 三个对象

| 对象 | 内容 | 位置 | 何时变化 | 身份 |
| --- | --- | --- | --- | --- |
| 框架镜像 | 操作系统层、受管的系统包、构建工具、EGL 厂商文件、入口脚本、编译入口。不含项目代码，不含 Python 虚拟环境 | 每台主机一个 | 主机受管环境变化时 | 镜像摘要、环境清单哈希 |
| Python 虚拟环境 | 解释器环境和全部 Python 依赖 | 主机目录，只读挂载 | Python 依赖变化时 | 目录内容哈希 |
| install 目录 | 项目代码的 colcon 安装产物 | 主机目录，按提交命名，只读挂载 | 每个提交 | 目录内容哈希、源码提交 |

shard 容器 = 框架镜像 + 挂载的虚拟环境 + 挂载的 install 目录 + 现有的数据和配置挂载。隔离方式不变：无网络、私有 IPC、只读
根文件系统、去除全部 capabilities。

推理服务容器保持现状，代码仍在其镜像内。

### 4.2 路径规则

install 目录和虚拟环境在主机和容器内以同一个绝对路径出现。原因是安装产物里的 setup 文件、CMake 配置和控制台入口脚本都写入
了绝对路径和解释器路径，换路径即失效。

因此：

- 现有入口里"安装前缀必须是 `/act/install`、解释器必须是 `/act/venv/bin/python`"的固定检查，改为核对规格文件给出的路径。
- 现有禁止把主机路径挂到安装路径之下的规则相应调整。
- 镜像内不再有 `/act/source`、`/act/install`、`/act/venv`。

### 4.3 多主机

每台主机一套：自己的环境清单、自己的框架镜像、自己的虚拟环境、自己编译的 install 目录。不跨主机共用框架镜像或 install 目录。

每次运行的证据记录主机标识和三个身份哈希，使不同主机采集的数据可以追溯到各自的环境。

同一提交在两台主机上是两份不同的二进制。两台主机采集的数据能否合并进同一个数据集，是数据层面的决定，本文只保证可区分。

两台主机的具体差异未知。实施的第一步是在两台主机上各运行一次清单工具并比对（第 8 节）。如果差异涉及 Ubuntu 大版本或 ROS
发行版，本文对那台主机不直接适用，需要另行设计。

### 4.4 macOS

直接在主机构建，只支持主机单 worker 执行。不使用容器，不生成框架镜像，不适用本文第 5 节的清单和锁定机制。

## 5. 环境一致

### 5.1 受管集合与环境清单

受管集合是 install 目录里的二进制在编译和运行时依赖的系统包，以及系统 Python 本身。集合定义写进仓库，随代码评审。初稿：

- `ros-jazzy-*`
- 项目声明的系统依赖
- 编译工具链
- `python3` 及其标准库包
- `libc6`、`libstdc++6`
- EGL 和 GL 相关库

集合只包含确有依赖的包，范围越大，第 5.3 节的代价越高。确切范围待实施第一步确定。

环境清单是对受管集合执行包管理器查询得到的"包名=版本"列表，规范化后求哈希。主机一份；框架镜像构建结束时在镜像内生成一份并
写入镜像。

内核和 NVIDIA 驱动不进受管集合：内核由主机和容器共用，驱动的用户态库由容器运行时从主机注入，两者天然一致。它们的版本记入每次
运行的证据。

### 5.2 同步脚本

一键完成以下步骤，任何一步失败即整体失败：

1. 生成主机当前的环境清单。
2. 取得主机当前已安装的受管包的 deb 文件本身。不按版本号去软件源查找，因为 ROS 软件源只保留最新版，主机升级几天后可能已
   无法取回同一版本。
3. 用这些 deb 构建框架镜像。
4. 在镜像内重新生成清单，与主机清单逐项比对；不相等则构建失败。
5. 记录镜像摘要、清单哈希、主机标识和时间。
6. 对受管集合执行锁定（第 5.3 节）。

### 5.3 受管包锁定

主机上会改动受管包的有三个来源：每天的自动升级、图形界面的软件更新、手动的安装或升级命令（包括安装别的包时的连带升级）。

采用 `apt-mark hold` 锁定受管集合。它对三个来源都生效，状态可查询，解除是一条命令。只配置自动升级的黑名单不够，它挡不住后两
个来源，而 2026-10-13 实际发生的正是后两个。

升级流程固定为：解除锁定 → 升级 → 运行同步脚本（重建镜像、比对清单）→ 重新锁定。同步脚本的锁定步骤需要管理员权限。

锁定是预防而不是保证：有管理员权限的人或程序仍可解除，显式指定版本安装也可绕过。真正的保障是第 5.4 节的拒绝规则。

代价：受管集合里的基础包（如 `libc6`、`python3`）被锁定后，其安全更新也不会自动安装，需要定期人工执行升级流程。

是否另外锁定内核和 NVIDIA 驱动以避免采集中途重启，是相关但独立的决定，本文不定。

### 5.4 拒绝规则

以下任一不成立即拒绝，不降级为告警：

准入时（主机侧）

- 主机当前环境清单的哈希等于框架镜像记录的清单哈希。
- 所选 install 目录的构建记录里，框架镜像摘要、清单哈希、虚拟环境哈希与当前一致。

容器入口

- 镜像内环境清单哈希等于规格文件给出的值。
- 挂载的 install 目录内容哈希等于规格文件给出的值。
- 虚拟环境的身份核对等于规格文件给出的值。

原生实例入口

- 与容器入口的后两条相同，另加主机当前清单哈希等于 install 构建记录里的值。

虚拟环境体积大，启动时全量计算哈希的耗时未测。可选做法是校验一份在虚拟环境定版时生成的文件清单；选哪种待实施时测量后确定，
无论哪种都必须能发现内容被改动。

## 6. 构建

### 6.1 编译入口

框架镜像内置编译入口。主机用框架镜像起一个临时容器，挂入源码快照、构建目录、目标 install 目录和虚拟环境，在容器内执行 colcon
构建。临时容器无网络，不使用 GPU。

目标 install 目录按提交命名。构建完成后设为只读，不原地重建。构建目录可以保留用于增量编译。

### 6.2 构建记录

构建结束时在 install 目录内写一份记录，至少包含：源码提交、源码快照哈希、框架镜像摘要、环境清单哈希、虚拟环境哈希、install
内容哈希、依赖清单。

这份记录取代现有的镜像内来源记录。取舍：现状下镜像里同时有源码和安装产物，可以互相印证；改后"安装产物确由这份源码编出"只由
构建记录声明，不再能在运行容器内重新验证。

### 6.3 主机门禁

主机门禁的构建步骤改用 6.1 的产物。门禁测试的对象与原生实例、shard 容器实际运行的是同一份二进制。

## 7. 运行

### 7.1 shard 启动

启动参数在现有基础上增加两个只读挂载：install 目录、虚拟环境。入口链不变，自检内容按 5.4 更换。规格文件增加三个身份字段和
两个路径字段。

### 7.2 原生实例

Linux 原生单 worker 使用同一个 install 目录和同一个虚拟环境。原生入口已有"代码必须来自给定安装前缀"的检查，沿用，并加上 5.4
的核对。

### 7.3 推理服务与 shard 的版本关系

推理镜像不再随提交重建，shard 侧的代码版本与推理镜像内的代码版本可以不同。因此：

- 去掉合同校验中两个镜像源码包哈希必须相等的要求。
- 推理请求协议需要版本标识或兼容性检查，使不兼容的组合在就绪阶段被拒绝，而不是在任务中途失败。现有协议是否已有这样的字段
  未核实。

### 7.4 身份与证据

现状下一个镜像摘要同时代表环境和代码。改后一次运行的受控身份由以下各项组成：框架镜像摘要、环境清单哈希、虚拟环境哈希、install
内容哈希、源码提交、推理镜像摘要、主机标识，以及原有的配置和策略哈希。

需要随之修改的记录：冻结合同的镜像与安装字段、就绪记录、来源读回记录、资格验证复算中引用镜像内安装哈希的各处。

正式采集时，install 目录和虚拟环境的身份纳入冻结输入。复现一次采集需要框架镜像、虚拟环境、install 目录三者齐备；归档和保留
策略待定。

现行方式和更早拓扑下的运行记录，按新代码不可读，只能用对应提交重读。

## 8. 实施顺序

获批执行后按以下顺序，每一步先有失败的测试再实现：

1. 清单工具；在 ai-station 和 antzb 各运行一次并比对；确定受管集合。
2. 同步脚本和框架镜像；验证镜像内清单与主机相等；受管包锁定。
3. 镜像内编译入口；产出 install 目录和构建记录；与主机直接编译的产物比对。
4. 路径规则、启动挂载、入口自检、规格与身份记录；去掉两镜像源码包哈希相等的要求；推理协议的版本检查。
5. 主机门禁改用容器内构建的产物。
6. 真实运行验证（第 9 节）。
7. 删除"代码烧进 shard 镜像"的路径及其测试、脚本和文档表述。

## 9. 验证

- 清单：主机与镜像逐项相等；人为改动一个受管包版本后，准入和入口都拒绝。
- 构建：同一提交、同一环境下两次构建的 Python、launch、配置文件逐字节相同；编译产物是否可复现要测量并记录，不预设。
- 拒绝规则：install 目录被改动一个文件、虚拟环境被改动一个文件、清单不一致，三种情况各自在准入和入口被拒绝。
- 真实运行，各用新的运行目录：
  1. 容器单 worker 八场景。
  2. 原生单 worker 八场景，使用同一个 install 目录。
  3. 两个 shard 容器并发，挂载同一个 install 目录。
- 完整主机门禁。
- 八路资格验证沿用既有计划，不在本文重新定义。

## 10. 风险

1. 环境一致是强前提。校验不严会出现比现状更隐蔽的不一致，因为现状下两边各自编译、各自自洽。对策是 5.4 一律拒绝。
2. 主机会在不知情时变化。对策是 5.3 的锁定加 5.4 的拒绝；锁定不能替代拒绝。
3. install 目录和虚拟环境是主机上的可变目录。对策：按内容命名、只读、启动时核对、正式采集时纳入冻结输入。
4. 安全边界从镜像扩大到主机上的两个目录：能写这些目录的人能决定容器内执行什么。
5. 受管包锁定会推迟基础包的安全更新。
6. 复现依赖三个对象齐备。
7. 改动覆盖已经验证过的容器链路，执行后要重新做第 9 节的真实运行验证。
8. shard 与推理服务的代码版本可以分离，协议不兼容的风险由 7.3 的检查承担。
9. 框架镜像成为主机专属，换主机不能直接复用。
