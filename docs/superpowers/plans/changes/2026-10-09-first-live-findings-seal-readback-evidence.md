# First live findings on the final freeze HRyCtQlG: start-of-stream losses, the second seal failure, the readback of INVALID results

Date: 2026-10-09 (CP-3394 follow-up to CP-3474)

Trigger: the final freeze ran L1 and S1 clean (rc 0, Teacher PASS) and showed three problems: L2 `e6be258c` ended rc 3 with the C5 gate firing and a new `RECORDER_SEAL_FAILED: AUDIT_WINDOW_INVALID` (P1), S2 `6b6efca6` ended rc 4 at `admit_pose` (P2), and the independent readback failed on every collection-on INVALID run (P3).

## P1(a). The per-topic losses on L2 are start-of-stream events (no code change; policy question open)

L2's recorder reported 7 losses, one on each of seven 500 Hz topics (`/clock`, the three controller states, `/joint_states`, `evidence`, `scene_state`). Five of them (those on topics the episode uses and with no gap in their own grid) failed the C5 gate as `reported=1 detected=0`.

- **When.** All seven `Messages lost on transport layer` lines of `bag-record.log` fall within 18 ms of each other, 3.29 s after `Starting recording` and 2.84 s before the window begins (sim 11.408 s). Each line is within 0-4 ms of that topic's first message in the bag (`/clock` loss at 693.1201 against first message 693.1201; neck 693.1268 / 693.1268; gripper 693.1313 / 693.1312; arm 693.1334 / 693.1334; joint states 693.1356 / 693.1356; scene_state 693.1378 / 693.1377). The first `/clock` message is sim 9.242 s; the window starts at 11.408 s.
- **The same pattern in all five fault bags** (`bag-record.log`, `f93d9fd4`, `ccb6b665`, `e9cb12f2`, `b728c111`): 5 to 7 high-rate topics each report exactly 1 loss within 15 ms of one another, 0.3 to 3.3 s after recording starts, and none of those bags shows a gap for them. The three losses the phase C investigation could not place on the old L2 bag `45315499` (7 reported, 4 placed) have the same shape: they were the start-of-stream events of the streams that did not have a gap to match.
- **Answers.** (1) The lost message lies before each topic's first recorded message, so outside the recorded range: the delivered sequence is gap-free from that first message to the last (publisher sequence, stamp grid and `camera_info` witnesses all complete), and the loss event is logged when that first message is delivered. (2) Yes, by the evidence: seven losses were reported and the delivered data has no gap behind any of them. The mechanism is inferred, not reproduced: the recorder subscribes to producers that are already publishing (in the old bags `publisher_sequence` starts near 296 and `chunk_sequence` at 19), and Fast DDS most likely reports the samples a reliable reader joining mid-stream never received as one event when the first sample arrives. Two synthetic tests did not reproduce it (a finite burst before the join; a 500 Hz volatile reliable Python publisher started before the recorder), so the production QoS (transient-local publishers, deep reader queues) or the C++ publisher timing matters and was not isolated. (3) Detection is not missing a gap: the grids are complete and nothing else in the bag is missing.
- **Why arm and neck "passed".** Their reported 1 matched an unrelated, real gap elsewhere in the bag (arm at 66.8 s, neck at 9.5 s): the rule `reported <= detected` is satisfied there by accident, which also shows that the rule cannot tell a start-of-stream event from an in-stream loss.
- **Recommendation (not applied).** Use the time information that already exists. Each loss line carries its log time, which is never earlier than the loss. A loss whose line was logged before the window begins (mapped through the bag's own `/clock` messages: sim 11.408 s is bag stamp 695.981 for L2) happened outside the window, so it is recorded, not judged; the C5 comparison `reported <= detected` then applies only to losses logged inside or after the window. L2 would then be VALID by rule (all 7 events are 2.84 s before the window). It needs the per-event times in the stats (`transport_lost_events`), parsed from the same log. The alternatives: leave the rule (every run loses at start, so every collection-on run is INVALID: not viable) or ignore the first loss of each topic (cannot tell a start event from a real first-message loss without the time). Implementing it is a policy decision.

## P1(b). `RECORDER_SEAL_FAILED: AUDIT_WINDOW_INVALID`: a window claimed without the first command (fixed)

Not new: it is on the golden L2 bag `45315499` since phase C (open point 4 of the transport-loss document); L2 `e6be258c` is the first live run to show it. Cause (reproduced with the processor, one reason, a patched `observed_collection_window`): reasons the scan latches before the replay (`preset_reasons`, here the loss) made `engine.invalid` non-empty from the start, and the engine retains Teacher events only while the data is valid, so the capture received no `phase_begin`. The rows were still captured; at the finish the audit claimed a window with `label_cutoff_s = 97.2` and `first_command_s = None`, outcome `complete`, which `_window_ok` refuses (a complete window needs a first command): the FAILED record could not be sealed, and the real reason was followed by a spurious second one.

Fix: the engine keeps a separate `replay_failed` flag that only reasons latched during the replay set. Retention of Teacher events, the tail, the reference check and the host's `invalid_latched` read `replay_failed`; the verdict, the seal status (`FAILED`, naming the first reason) and the result still read `invalid`. Scan-level reasons no longer stop the replay from delivering the events the seal needs. First attempt (events only) produced `ACT_DATA_ALREADY_INVALID` and `WORLD_SOURCE_NATIVE_REQUIRED` because the host refused a finish when `engine.invalid` was non-empty; the host seam now reads `replay_failed`.

Effect on the eight golden inputs: seven are unchanged (verdicts, reasons, no sealed episode); `45315499` loses `RECORDER_SEAL_FAILED: AUDIT_WINDOW_INVALID` and now has a sealed episode (`FAILED`, `RECORDER_DATA_INVALID: OFFLINE_TRANSPORT_LOSS_UNATTRIBUTED: ...`). Test: `test_a_scan_level_loss_leaves_a_sealed_failed_record_not_a_second_seal_failure` (RED: the second reason; GREEN: sealed FAILED).

## P2. S2 `RUNNING_EVIDENCE_UNAVAILABLE` (cause not shown by the retained evidence; no link to this change; diagnostics added)

- **Where.** `ParallelRosRuntimePorts.capture_numeric_evidence` waits up to 5 s for a fresh, unpaused, session-matching `SimulationEvidence` with `simulation_time_s >= image stamp` (7.0 s) from a new `MujocoWorldObserver`. Perception had finished: the pose (0.02012, -0.28044, 0.165) was accepted at 22:18:10.445, equal to the pinned-era poses, so R6, the unpin and the query change are upstream of the failure. The run's code path from the pause to the wait (pause control, observer) was not touched by CP-3473 (`git diff` of `backends/` and `ros/` is empty for that change).
- **What the world did.** `ros2_control_node` log: paused 90.3026 (inference hold), resumed 90.4629, then 480-500 evidence messages per second until shutdown at 105.5. The wait began at 90.462 and ended at about 95.5 with the world running throughout, so the observer saw nothing it accepted for 5 s while the producer was healthy.
- **History.** 174 live experiment roots in this evidence root; `RUNNING_EVIDENCE_UNAVAILABLE` appears once (S2). Other admit_pose boundary failures exist (`CONTACT_STALE` twice, `TEACHER_PHYSICS_SOURCE_REFUSED`, `TEACHER_EXECUTION_HOLD_SOURCE_INVALID`, a timeout), so start-up races at this boundary are not new. L1, S1 and the pilots took 30 ms from pose to `physical.json` (sim 7.5 and 8.2 s).
- **Not proven.** Candidates that fit the log and that the code allows: the observer's transient-local cached sample is a paused message and the live messages that follow are rejected (`EvidenceRejected` is swallowed in the callback and shows only as a stale `snapshot()`), or the shared node's executor did not deliver. The run kept nothing that tells them apart (the failure was the bare code). No live stack was started in this round.
- **Change.** The failure now carries what the observer saw: `RUNNING_EVIDENCE_UNAVAILABLE: {callbacks, rejected, last_rejection, publishers, latest: {paused, simulation_time_s, age_s, ...}, minimum_simulation_time_s}` (new `MujocoWorldObserver.latest_summary()`; the timeout is a class attribute for tests). The code prefix is unchanged. Tests: three in `test_parallel_ros_runtime.py` (silent, stays paused, returns the first unpaused message). No retry was added: a repeat would hide the occurrence rate.

## P3. Readback of a committed INVALID result without a QC report (decision CP-3394, implemented)

- `act_first_episode readback` now runs `verify-commit` first. When the verified commit proof says `act_data_status INVALID`, `act_data_qc NOT_RUN` and binds no QC report, and the result holds no `qc-report.json`, the QC stage is `NOT_APPLICABLE` (rc 0, reason `COMMITTED_INVALID_WITHOUT_QC...`), no recomputation is made, and the receipt says `qc_applicability: NOT_APPLICABLE`. A result that holds a report the proof does not bind is a failed QC stage, not N/A.
- `check-export` (diagnostic runs): the two common boundaries are tried; an entry that resolves must be refused (`DIAGNOSTIC_EPISODE_NOT_TRAINABLE`) and the proof is written as before; when nothing resolves (`EPISODE_COLLECTION_IDENTITY_INVALID` on the live roots) the stage is `NOT_APPLICABLE` with the reasons; an entry that exports is `DIAGNOSTIC_EXPORT_UNEXPECTEDLY_ELIGIBLE`, rc 3. Standalone `check-export` prints `NOT_APPLICABLE`, rc 0.
- Receipt: `qc_recomputations 0` is allowed only with N/A and then required to be 0 (`READBACK_RECOMPUTE_COUNT` otherwise); N/A without the supporting proof is `READBACK_QC_NOT_APPLICABLE_UNSUPPORTED`; status PASS, readback rc 0.
- Wrapper: `judge_readback_receipt(receipt, pid, live_root, expect)` in `act_first_episode.py` is the single judge; `expect` is `INVALID` for a live rc 3 and `VALID` for rc 0. An N/A receipt is accepted for INVALID only; VALID still needs exactly one recomputation and agreeing digests. New wrapper `run-qualified-live-20261010-r11.zsh` (next to r10, which is unchanged) calls it.
- Tests (RED against CP-3473: 6 failures): committed INVALID without episode reads back clean with 0 recomputations; the commit is still verified (a missing commit still fails); a resolvable entry must be refused and an eligible one fails; N/A with a report present fails; zero recomputations without N/A fails; the wrapper rules for both outcomes.
- Offline readback of the six existing live roots (`e6be258c`, `c5decb3a`, `e9cb12f2`, `b728c111`, `f93d9fd4`, `ccb6b665`; `writer-artifacts/phased/readback-six/`): all six now readback_rc 0, receipt PASS, qc and check-export NOT_APPLICABLE, verify-commit PASS, and `judge_readback_receipt(..., expect="INVALID")` empty.
